# 图像区域工具（已实现）

> 给 AI 助手两个看图工具：`image_info`（纯文本的文件事实）和 `view_region`
> （把一块区域放大再发给模型）。这份文档记的是**为什么这么做**，以及两条
> 只有真跑起来才会暴露的解码器事实——那两条各自都能让功能"看着实现了、其实没生效"。
>
> 文末另有一节记**助手改标签的能力边界**（"覆盖"曾经做不到，以及它为什么看起来像
> "做了但没生效"）——同一类问题：**模型声称的事与这条工具真正能表达的事不一致**。

## 要解决什么

整图被缩到长边 1024 再发给模型（实测 4000×6500 → 630×1024），细节全糊。
裁一块区域再缩到 1024，模型能看清的信息量是完全不同的量级。所以给助手一个
"把某个区域放大给我看"的工具。

## 两个工具

| 工具 | 参数 | 行为 |
|---|---|---|
| `image_info` | 无 | 返回文件名、格式、文件大小、原始像素尺寸（含 EXIF 方向）、这次被缩到多小、已有几个标签 |
| `view_region` | `mode=crop`：`x,y,w,h` | 裁一块，作为**一条新的 user 消息**附带图 |
|  | `mode=tiles`：`cols,rows` | 按网格均分，`cols*rows ≤ 9` |

设计要点：

- **坐标一律归一化（0–1）。** 模型看不到原始分辨率，让它填像素等于让它猜；
  归一化之后 `x=0.4,w=0.2` 这种它推得出来。`w/h` 是**尺寸**不是右/下边界——
  说明里单独写了一句，实测这种混淆是模型最容易犯的那个。
- **`tiles` 块数封顶 9（3×3）。** 每张约 100–150 KB 且**各自算 token**
  （1024 长边约 850 token），4×4=16 张足以把上下文顶爆。上限写在工具说明里。
- **一次对话总共封顶 12 张放大图**（`TagAgent.MaxRegionImages`）：3×3 用掉 9 张，
  再留 3 张给"再裁一处"。用光了如实告诉模型用完了，让它拿现有的图作答。
  这个上限是必要的——插进 `messages` 的图**会在本次 RunAsync 的后续每一轮请求里重复出现**。
- **没带图时不下发 `view_region`。** 放大的图只能靠"往对话里插图文消息"送出去，
  而这次没带图（用户关掉了「带当前图片」）时那条路等于绕过用户的开关偷偷发图。
  `image_info` 仍然下发——它纯读纯文本，没有这个顾虑。
- **用完即焚。** 图只活在这一轮的 `messages` 里：不落盘、不进 `AgentChatStore`、
  下一轮要看就再调一次。这正是"需要再裁"的语义。

## 消息构造：为什么图要放在本轮**所有**工具结果之后

OpenAI 兼容协议的硬约束：工具结果只能是文本（`ToolMessage(call.Id, text)`），
而且 `tool` 消息必须**紧跟**要它的那条 `assistant`。所以"把裁好的图给模型看"
只能走"再插一条 user 消息"：

```
assistant(tool_calls: view_region)
tool     ("放大的区域已附在下面…")        ← 只能回文字
user     ("你要的放大区域在下面", [图])   ← 图在这里
```

插入点**必须等这一轮所有工具调用都处理完**，不能紧跟在这个 `view_region` 的结果后面：
模型一轮里同时发多个工具调用时，那条 user 消息会插进 `tool` 消息中间，
严格的网关直接 400。所以实现上是"先攒起来（`pendingImages`），foreach 之后再插一条"。

那条 user 消息的文案也写了"这是你要的放大区域，不是用户新说的话"，
系统提示里同样重申了一遍——否则模型会去**回答**那条消息。

## 先验证再写：为什么差点白做

动手前先拿真实 key 实测了三个报文形状（探针见 `tests/RegionProbe.cs`，
`corecheck region`）：

| 形状 | 结果 |
|---|---|
| 图挂在第一条 user 消息上（对照组） | 读对了 |
| **图挂在后插的一条 user 消息上**（`view_region` 的形状） | 读对了 |
| 一条消息里两张图，问它第二张（`tiles` 的形状） | 读对了 |
| 真实 `TagAgent` 循环里模型自己调 `view_region` 认字 | 调了、拿到了、读对了 |

那个探针还有一处刻意的设计：**逐轮把"这一轮报文里有几张图、模型调了什么、回了什么"
打出来**。模型没读出字时，只有这张表能指出断在哪一层——是图没插进报文（产品的错），
还是插进去了模型没看（模型的事）。第一次跑就靠它区分开了。
（探针用的是真实模型，字读不读得出来会偶发抖动，所以它不属于默认套件。）

## 两条只有实测才会暴露的解码器事实

裁剪碰 WinRT 的 `BitmapDecoder`。两处文档说得含糊、实测与直觉相反的地方，
**猜错的症状都不报错**，所以这里只写实测结论，验证命令留在
`tools/imgprobe/`（下面有复现方式）。

### 1. `ScaledWidth/Height` 先把**整幅**缩了，`Bounds` 再在缩放后的坐标系里裁

不是"先裁一块再放大"。实测（本机 JPEG 解码器，`imgprobe bounds`）：

| 调用 | 结果 |
|---|---|
| 裁 (0,0,300,200)，不缩放 | 得到原始左上那一块（对） |
| 裁 (300,0,300,200)，缩放到 300×200 | **`E_INVALIDARG`**（裁到缩放后的图外面去了） |
| 裁 (0,0,300,200)，缩放到 300×200 | 得到**整幅的缩小版**——尺寸也是 300×200，看着完全正常 |

最后一行就是那个坑：尺寸恰好一样，只有取像素才认得出。
所以裁剪路径**解码时绝不给 `ScaledWidth/Height`**（只给 `Bounds`），
缩放交给编码器（`BitmapEncoder.BitmapTransform`，那里没有 Bounds，语义只有一种）。

### 2. 请解码器转正时，那两个缩放数字解释在**转正之前**的坐标系里

`LoadAsync`（整图那条既有路径）一直是这么写的：

```csharp
var (ow, oh) = ImageSizing.Oriented(rawW, rawH, orientation);   // 转正后的宽高
var (tw, th) = ImageSizing.Fit(ow, oh);
transform.ScaledWidth = tw; transform.ScaledHeight = th;        // ← 错的
```

实测：竖图 400×800 + EXIF 6（显示时该是 800×400），这么写拿到的是 **400×800**，
而且画面被横向拉伸一倍——用"正圆变没变椭圆"才看出来（纯色象限图判不出拉伸：
四个象限在两种长宽比下相对位置完全一样）。正确做法是按**未转正**的宽高算缩放
（两者只差一次交换，比例不变），尺寸取解码器实际给出来的：

```csharp
var (tw, th) = ImageSizing.Fit(rawW, rawH);                     // 未转正
... var bmp = await decoder.GetSoftwareBitmapAsync(... RespectExifOrientation ...);
return new EncodedImage(bytes, bmp.PixelWidth, bmp.PixelHeight); // 以解码器为准
```

**这是本次改动修掉的一个既有缺陷**：EXIF 方向为 5–8 的照片发出去是变形的
（此前只有"方向要算进去"那句注释，没有对应的验证）。方向为 1 的图不受影响，
所以画稿（PNG、无 EXIF）从来没暴露过它。

### 3. 旋转放在托管代码里做，不依赖解码器的方向开关

裁剪路径（`CropManyAsync`）里：**按原始像素裁 → 托管代码转正 → 编码时缩放**。
三步各自的语义都是确定的。旋转那一步是 `ImagePixels.Orient`（纯逻辑、逐像素可断言），
连"行距大于宽×4"这种解码器行为都有断言——按 宽×4 去索引会逐行错位，
画面呈现为斜的彩色条纹，那种错的成因一眼看不出来。

`ImageRegion.ToRaw` 负责"模型给的（转正后）坐标 → 解码器原始像素坐标"的**反查**：
EXIF 方向的含义是"从原始像素到正确显示要做什么"，这里要的是它的逆。
用边缘坐标推，所以那个恼人的 `-1` 不出现在任何一条里；方向 5–8 要交换宽高。

## 怎么复现这些结论

```powershell
# 1. 生成探针图片（四象限纯色 + 带圆的竖图/大图 + 两张写字的）
python tools/imgprobe/make_probe_images.py

# 2. 取像素核对：象限对不对、EXIF 方向有没有应用、圆有没有变成椭圆
dotnet build -c Release tools/imgprobe/imgprobe.csproj
python tools/imgprobe/check.py

# 3. 真实网络：三种报文形状 + 真实 TagAgent 循环（要已配置接口与 key）
tests\bin\Release\net10.0\corecheck.exe region
```

第 2 步的判据全是**像素数字**而不是肉眼：四象限图的中心像素、白圆的宽高差。
它是被"尺寸恰好一样"那一次逼出来的——那一次所有尺寸断言都通过，
只有像素不对。

## 已知限制

- **模型看不出"这是放大图还是整图"。** 它收到的是同一张图的一部分，
  系统提示和那条 user 消息都只能"说"这件事。实测里它偶尔会把放大块当成整张画面
  （回答写"整张图是一行黑字"）。目前靠文案压着，没有更强的机制。
- **`image_info` 只报当前这张图**，不支持按名字问别的图（要换图得先 `select_image`）。
- **放大不会超过原图分辨率**：`Fit` 不放大（放大只会让模型看到插值出来的假细节），
  所以一块本来就 ≤1024 的区域拿到的是原尺寸。文案里会如实说"没有变大"，
  避免它反复裁同一块。

## 助手改标签的三个通道（补上的删除）

用户报过一个现象：**连让助手"覆盖"两次，它每次都说覆盖了，而标签列表看着没变。**
在真机上复现（`corecheck overwrite`，本地模型）后，成因有两层，都不是"模型不听话"：

### 1. 它**没有手段**表达"删掉那些"

`propose` 原来只有 `add_tags` 一个通道。用户说"把标签覆盖成这三条，原来那些不要了"
时，模型发出的仍然是：

```json
{"add_tags":["solo","smile","upper body"],"note":"将标签替换为用户指定的三个标签"}
```

它**只能往里加**，却在 note 里写了"替换"——因为它确实想替换，而工具里没有那个动作。
落地的结果是 16 个现有标签一个没少。这不是提示词能修的：**能力边界不在提示词里，
在工具声明里。**

补上 `remove_tags` 之后，同一个探针、同一个模型：

```json
{"remove_tags":[13 个旧标签],"add_tags":["solo","smile","upper body"]}
→ (现有 16 − 删 13) ∪ 加 3 = 正好是用户要的三条
```

**为什么用"删哪些 + 加哪些"而不是直接给出最终列表（`set_tags`）**：后者一旦模型少写
一个标签就会**静默清掉**一条真实标注；而逐条列出的删除在提案卡片上看得见、能核对，
漏了也只是"没删干净"。这个取舍与「Unknown 不丢弃」同源——宁可留下东西，不可静默删。

### 2. 它**看不到**现有标签

`current_image` 原先只报数量（`It already has a caption with 16 tag(s)`）。
想删也没法点名——它连是哪 16 个都不知道。现在把当前那张图的标签**原样列出**，
并写明"要删就放进 remove_tags"。只给当前那张：其余图列出来既费上下文也没用。

### 3. 实测里那些"看着没变"的时刻，有一半是正确行为

把应用 — 保存 — 再应用整条链在界面里走了一遍（UIA 驱动真程序），日志与列表如下：

| 步骤 | 标签列表 | 盘上 `.txt` |
|---|---|---|
| 起点 | 1girl, solo, blonde hair, twintails, blue eyes | 同左 |
| 覆盖成三条 | **solo, smile, upper body** | 没变（**应用只改内存**） |
| 按保存 | solo, smile, upper body | **solo,smile,upper body** |
| 再覆盖一次 | solo, smile, upper body | 同左 |

第四行是关键：**它上次已经覆盖成那三条了**，所以第二次 `tags+=0 tags-=0` ——
"看着没变化"是**正确**的。而第二行那个"列表变了、文件没变"才是真的坑：
界面上那句提示原先写的是「已按完全权限直接写入」，读者自然以为文件也写了。
现在改成「**还没保存到文件**——按 Ctrl+S 才写进 .txt」。

（顺带一条判断经验：这类投诉先分清是"没改"还是"没存"。`agent applied: tags-=N`
看内存那一步，盘上文件的 mtime 看落盘那一步，两者一比就知道断在哪。）

## 预算：写死的那个数字，和"以为生效了"的设置

用户报"token 上限才 8192，复杂打标完全不够用"。查下来比这更糟：

| 路径 | 原来 | 现在 |
|---|---|---|
| AI 助手 | **写死 2400**（`TagAgent.Budget`） | `AgentMaxTokens`，**默认 0 = 自动** |
| 问模型找标签 | 写死 1600 | 0 = 自动（`LlmClient.ToolAutoFallback` 兜底） |
| 翻译 / 短任务 | 读 `cfg.MaxTokens` | 不变（默认 400） |
| 界面上限 | `NumberBox.Maximum = 8192` | 1048576 |

**"8192 不够用"这个说法本身就说明问题**：助手压根没读那个设置，它是 2400。
所以"调大一点"既没用（那条路读不到）、也调不大（界面卡在 8192）——
而用户完全无从察觉，因为设置框里明明写着一个更大的数。

现在 0 = 自动：按服务端 `/models` **自己声明**的能力算，优先 `max_output_tokens`，
没有则取 `context_window` 的一半，都没有才兜底。实测本机那份配置：

```
助手预算 = AgentMaxTokens=0 -> 实际发送 393216（自动：服务端 max_output_tokens）
```

### `save_caption` 与一个"押在模型身上"的错误设计

加这个工具时第一版是"模型调它 → 当场写盘"。两个问题：

1. **当场写盘写的是旧内容。** 调 `save_caption` 那一刻提案还没应用
   （`propose` 一调循环就结束，应用在循环返回之后），所以存下去的是上一次的内容
   ——而它会回报"保存成功"。
2. **模型根本不调它。** 修好第 1 点（只记意图、挂在提案上、由界面在应用后写）之后，
   端到端还是失败：给它下发了工具、要求里明确写"改完直接保存到文件"，
   它那一轮 **calls 里一次都没有 save_caption**（日志 `round=1 calls=4`、
   `round=2 calls=1`）。

第 2 点是设计问题，不是提示词问题：**「完全权限」对用户的承诺是"不用我管"，
而"要不要落盘"取决于模型记不记得调某个工具，等于把承诺押在它身上**。
所以改成程序保证——完全权限下应用提案之后**直接存**，与 `Ctrl+S` 同一条路；
模型显式调了 save_caption 也一样走这条路（那条只设标记）。两种意图结果一致。

端到端复验（真模型 + 真界面）：

```
one.txt 初始 = existing, marker
agent applied: tags+=3 tags-=2 total=3
agent save_caption: ok=True Saved "one.jpg" to disk.
agent full-access write+save ok=True modelAsked=False
one.txt 之后 = solo, smile, upper body      ← 文件真的变了
```

`modelAsked=False` 那行是重点：**模型没调工具，但文件照样写对了**。

## 批量自动打标

「浏览 → 自动标注未标注的图片…」，走的是**同一个 TagAgent**（同一套提示词、
工具、预算、保存逻辑），只换了驱动方式。三处刻意的决定：

- **默认只处理没有 `.txt` 的图。** 批量最常见的用法是"把新收的图过一遍"，
  默认重做全部等于覆盖用户精修过的标注，而那是不可逆的。想重做要显式取消勾选，
  确认框里会写清"其中 N 张已有标注、会被覆盖"。
- **每张图独立一轮对话**（历史只有这一句）。带着上一张的上下文会让模型拿前一张的
  画面描述这一张，而它**看起来还在正常工作**——这是最难查的一类错。
- **一张失败不中断**，记下来接着跑，最后分类报告：写入 / 无需改动 / 没提案 / 失败。
  "模型没提案"与"失败"必须分开：前者是合法结果（这张图没什么可写），
  混在一起用户就分不清"跑完了"和"跑挂了"。

范围选择与记账是纯函数（`Core/BatchPlan.cs`），所以"会动哪几张、结果怎么数"
能在回归里直接断言——这正是最该钉住的部分：选错范围会改写用户的训练集。
