# 架构与设计取舍

> 这里放的是「**为什么这么写**」的理由。用户不需要知道，后来的维护者需要。
> 与 `NOTES.md` 的分工：那边记「只有真跑起来才暴露的坑」，这边记**结构上的决定**。

## 为什么只有一个 exe（标注模式 + 写标签模式）

写标签模式要复用的正是这个程序的主体：词库校验、大类分段、`Tab` 补全、标签搜索、
中英对照、中文 → 英文翻译、大类配色、提示词解析与着色——这些**本来就不读当前图片**，
它们只吃「当前这段提示词」。实测所有标签操作（上移、删除、校验、规范、模型补译、粘贴）
没有一处碰当前图片，唯一耦合的只有「从哪个文件读、写回哪个文件」。

所以两个模式共用一份控件和一份代码，差异收敛成四件事：

| | 标注模式 | 写标签模式 |
|---|---|---|
| 左栏 | 图片列表 | 提示词库（历史 + 预设） |
| 当前文档 | 训练集里的一张图 → `.txt` | 内存里的一段草稿 → 提示词库 |
| 主操作（`Ctrl+S`） | 写回同名 `.txt` | 复制整行到剪贴板 |
| 菜单 | 浏览 / 标签 / 工具 | 提示词 / 标签 / 工具 |

拆成两个 exe 的代价是两份约 40 MB 输出、`settings.json` 的互相覆盖（`Save()` 是
整份内存对象覆盖写，且程序没有单实例锁，两个进程会静默回滚对方改过的设置），
以及 `.pri` 资源那套打包坑；收益只是省掉上面这张表里的分派。

判断标准：**写标签模式里"没有训练集概念"的部分占比会不会超过一半。** 只要它主要
还是"组装一段提示词然后复制走"，同 exe 就更省；若它长成带队列/图库/批量的出图前端，
就该拆成 `AnimaCore` 类库 + 两个 thin exe。注意 `tests/corecheck.csproj` 是
**net8.0**、靠直接编译 `Core/*.cs` 做回归，库若只 target `net10.0` 就会丢掉那份
"直接编译真实源码、改错就被测到"的特性，所以库应多目标 `net8.0;net10.0`。

## 提示词库为什么不塞进 `settings.json`

那是配置，而这是**会随使用增长的数据**。`AppSettings.Save()` 是整份内存对象覆盖写，
把历史塞进去等于每复制一次提示词就重写一遍全部设置，而且写历史这件事不该触发整份
配置落盘。所以 `PromptLibraryStore` 独立成
`%LocalAppData%\AnimaCaptioner\prompts.json`（仿 `ModelGlossStore` 的做法）。

## 分类只有一份，排序策略保留两份

仓库里并存两条排序路径，它们**不是重复实现**：

| | `TagSections.Canonicalize`（界面用） | `VocabDb.Arrange`（自动排） |
|---|---|---|
| 调用方 | 标注与写标签模式的界面 | 写标签模式的「按热度自动排段内顺序」 |
| 段内顺序 | **原样保留**人工排的 | 按 `prior`（训练集里的平均相对位置）重排 |
| 服务场景 | 改已有文件，人已经排好了 | 生图从零组装，手边没有排好的顺序 |

两条路冲突的地方，恰好是两个模式需要相反行为的地方，所以**段内策略有意保留两份**。

但**分类**必须只有一份真源。原先 `VocabDb` 里另抄了一份 `HeadGroups`，结果是两套
分类各自漂移：那一份压根没有**元信息**组，于是 `highres` / `absurdres` 找不到归属、
掉进 body 被按热度排进一般标签里。现在 `Arrange` 的分类统一向 `TagSections` 要
（见 `Core/VocabDb.cs` 排序一节的注释），那边加一个词这边自动跟上。

> ⚠️ **这里有意偏离了 Python 参考实现。** `animatag.py` 的 `HEAD_GROUPS` 只有
> `[QUALITY, SCORE, YEAR, RATINGS, COUNTS]` 五组、没有元信息组，所以它在同样输入下
> 也会把 `highres` 排进正文。`tests/Sections.cs` 的断言 `[8]` 专门钉住这条偏离，
> 因为 `parity` 的三个 golden 用例里**一个元信息词都没有**，一直没覆盖到——
> 这正是这个 bug 能长期藏着的原因。
>
> 重跑 `analyse\gen_golden.py` 会按参考实现的旧行为重新生成 arrange 用例，
> 需要人工保留本修复，或同步改 `animatag.py`。

## 第一段为什么拆成四段

官方把 `quality/meta/year/safety` 写成同一个方括号，配合 `arbitrary order`，拆与不拆
都合规（详见用户文档 [标签顺序与分段](../04-tag-order.md)）。工程上的理由是这三条：

- 安全词有**独立于词库的档位校验**（`SafetyRating`），单独成段才能和它的校验语义对齐；
- 四类的**判据来源不同**（质量 / 元信息来自模型卡逐条列举，安全来自 Danbooru 评级规范），
  耦合在一段里改一处会牵动另一处；
- 安全词表原先在两处各写一份且**已经分叉**（`TagSections` 有 `questionable` 没 `general`，
  `SafetyRating` 反过来）。拆成独立段时顺手合并成一处：
  `SafetyRating` 改为复用 `TagSections.SafetyWords`。

## 分栏比例为什么按模式各存一套

两个模式的分栏语义不同（图片 / 标签 / 提示词 vs 提示词库 / 标签 / 提示词），
共用一组值会让一个模式里拖过的布局把另一个模式改掉。

## 中栏宽度下限为什么是 240 DIP

这是量出来的，不是随手定的：再窄下去底部的「上移 / 下移 / 删除 / 校验」四个按钮
会被裁掉。
