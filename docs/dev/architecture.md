# 架构与设计取舍

> 这里放的是「**为什么这么写**」的理由。用户不需要知道，后来的维护者需要。
> 与 `NOTES.md` 的分工：那边记「只有真跑起来才暴露的坑」，这边记**结构上的决定**。

## 为什么只有一个 exe（标注模式 + 写标签模式）

写标签模式要复用的正是这个程序的主体：词库校验、大类分段、`Tab` 补全、标签搜索、
中英对照、中文 → 英文翻译、大类配色、提示词解析与着色——这些**本来就不读当前图片**，
它们只吃「当前这段提示词」。实测所有标签操作（上移、删除、校验、规范、模型补译、粘贴）
没有一处碰当前图片，唯一耦合的只有「从哪个文件读、写回哪个文件」。

所以两个模式共用一份控件和一份代码，差异收敛成四件事：

| | 标注模式 | 写标签模式 |
|---|---|---|
| 左栏 | 图片列表 | 提示词库（历史 + 预设） |
| 当前文档 | 训练集里的一张图 → `.txt` | 内存里的一段草稿 → 提示词库 |
| 主操作（`Ctrl+S`） | 写回同名 `.txt` | 复制整行到剪贴板 |
| 菜单 | 浏览 / 标签 / 工具 | 提示词 / 标签 / 工具 |

拆成两个 exe 的代价是两份约 40 MB 输出、`settings.json` 的互相覆盖（`Save()` 是
整份内存对象覆盖写，且程序没有单实例锁，两个进程会静默回滚对方改过的设置），
以及 `.pri` 资源那套打包坑；收益只是省掉上面这张表里的分派。

判断标准：**写标签模式里"没有训练集概念"的部分占比会不会超过一半。** 只要它主要
还是"组装一段提示词然后复制走"，同 exe 就更省；若它长成带队列/图库/批量的出图前端，
就该拆成 `AnimaCore` 类库 + 两个 thin exe。拆的时候别破坏回归方式：`tests/corecheck.csproj`
靠**直接编译 `Core/*.cs` 真实源码**（不是引用编译产物）来做对拍，所以库的 TFM 必须能被
测试工程引用——两边现在同为 **net10.0** 代际（应用是 `net10.0-windows10.0.19041.0`，
测试是纯 `net10.0`），换代际时两边要一起动，否则"改错就被测到"那份特性会丢。

## 模型站点：顶层四个字段是**视图**，不是存储

地址 / 密钥 / 模型名 / 推理档位现在按**站点**成组存（`Core/ModelProfile.cs`），
`AppSettings` 上那四个同名属性变成"当前活动站点"的视图：

```csharp
public string ApiBaseUrl { get => ActiveProfile?.BaseUrl ?? ""; set => ActiveOrNew.BaseUrl = value; }
```

这个形状解决两个问题，两个都是**会静默出错**的那类：

1. **换服务不该要改四处。** 本地 llama-server 与云端之间这四项全都不一样，档位甚至
   是相反的（前者靠 `enable_thinking`、只认「关闭思考」；后者认 8 档 `reasoning_effort`）。
   拆成四个独立输入框时，每换一次服务改漏一处就是一次 401 或一个不生效的档位。
2. **调用方零改动。** `LlmClient` 的每个方法、`TagTranslator`、`TagSearchAgent`、
   `AgentHost`、`MainWindow` 一共 50 多处都从 `cfg` 读这四个名字。做成视图之后，
   那些调用一行都不用动，也就不可能出现"某个调用点还在读旧字段"这种漏网。

代价是**迁移必须正确**，而它一旦写错是静默的（密钥变空、地址回默认），所以：

- 迁移的判据是后备字段 `_profiles is null`，**不是 `Profiles.Count`**。后者不行：
  getter 在表为空时会自动补一个默认站点（保证四个视图属性永远有落脚点），于是
  "旧配置里没有这张表"与"表在但是空的"变得无法区分，迁移会以为已有站点、
  转头把旧配置丢掉。反序列化时 JSON 里没有 `Profiles` 键就不会调 Setter，
  所以那个 null 正是"旧配置"的信号。
- 迁移走完把旧顶层键置 null；配合 `WhenWritingDefault`，下次保存它们就消失。
  测试直接解析序列化结果的**根对象**来验证（不能在整串里搜 `"ReasoningEffort"`——
  站点条目内部本来就有这个键，那种检查必然误报）。
- 密文**原样搬运**（不解密再加密，少一次经手），搬完要 `ForgetCachedKey()`：
  `ApiKey` 的 getter 只解一次并缓存，不丢缓存的话那份密钥读出来永远是空。

设置对话框在**副本**上编辑（`ModelProfile.Clone()`），`ApplyTo` 时才整表写回
（用 Setter 整体替换，不要 `Clear()` + `AddRange()`——getter 的兜底会在中间塞一个
默认站点，结果多出一条用户从没建过的）。这样「取消」是真的取消：直接在真配置上改的话，
删掉一个站点又点取消，那个站点的密钥已经从内存配置里没了。

`AgentHost` 之外，助手面板里还有一个模型选择器（`MainWindow.AgentModel_Click`），
列的是站点 × 档位，选完立刻 `Save()`。放在面板里的理由是任务级的：对话中途换模型
是最常见的动作，而要为此打开设置、翻页、点保存，代价大到用户干脆不换。

## 提示词库为什么不塞进 `settings.json`

那是配置，而这是**会随使用增长的数据**。`AppSettings.Save()` 是整份内存对象覆盖写，
把历史塞进去等于每复制一次提示词就重写一遍全部设置，而且写历史这件事不该触发整份
配置落盘。所以 `PromptLibraryStore` 独立成
`%LocalAppData%\AnimaCaptioner\prompts.json`（仿 `ModelGlossStore` 的做法）。

## 分类只有一份，排序策略保留两份

仓库里并存两条排序路径，它们**不是重复实现**：

| | `TagSections.Canonicalize`（界面用） | `VocabDb.Arrange`（自动排） |
|---|---|---|
| 调用方 | 标注与写标签模式的界面 | 写标签模式的「按热度自动排段内顺序」 |
| 段内顺序 | **原样保留**人工排的 | 按 `prior`（训练集里的平均相对位置）重排 |
| 服务场景 | 改已有文件，人已经排好了 | 生图从零组装，手边没有排好的顺序 |

两条路冲突的地方，恰好是两个模式需要相反行为的地方，所以**段内策略有意保留两份**。

但**分类**必须只有一份真源。原先 `VocabDb` 里另抄了一份 `HeadGroups`，结果是两套
分类各自漂移：那一份压根没有**元信息**组，于是 `highres` / `absurdres` 找不到归属、
掉进 body 被按热度排进一般标签里。现在 `Arrange` 的分类统一向 `TagSections` 要
（见 `Core/VocabDb.cs` 排序一节的注释），那边加一个词这边自动跟上。

> ⚠️ **这里有意偏离了 Python 参考实现。** `animatag.py` 的 `HEAD_GROUPS` 只有
> `[QUALITY, SCORE, YEAR, RATINGS, COUNTS]` 五组、没有元信息组，所以它在同样输入下
> 也会把 `highres` 排进正文。`tests/Sections.cs` 的断言 `[8]` 专门钉住这条偏离，
> 因为 `parity` 的三个 golden 用例里**一个元信息词都没有**，一直没覆盖到——
> 这正是这个 bug 能长期藏着的原因。
>
> 重跑 `analyse\gen_golden.py` 会按参考实现的旧行为重新生成 arrange 用例，
> 需要人工保留本修复，或同步改 `animatag.py`。

## 第一段为什么拆成四段

官方把 `quality/meta/year/safety` 写成同一个方括号，配合 `arbitrary order`，拆与不拆
都合规（详见用户文档 [标签顺序与分段](../04-tag-order.md)）。工程上的理由是这三条：

- 安全词有**独立于词库的档位校验**（`SafetyRating`），单独成段才能和它的校验语义对齐；
- 四类的**判据来源不同**（质量 / 元信息来自模型卡逐条列举，安全来自 Danbooru 评级规范），
  耦合在一段里改一处会牵动另一处；
- 安全词表原先在两处各写一份且**已经分叉**（`TagSections` 有 `questionable` 没 `general`，
  `SafetyRating` 反过来）。拆成独立段时顺手合并成一处：
  `SafetyRating` 改为复用 `TagSections.SafetyWords`。

## 转义为什么只做圆括号、且判据是词库

`Core/TagEscape.cs` 只把 `(` `)` 转成 `\(` `\)`。这不是照搬 A1111 的习惯，而是照着
ComfyUI 的解析器实测出来的：`comfy/sd1_clip.py` 里 `escape_important` 只处理
`\(` `\)`，`parse_parentheses` / `token_weights` 也只跟踪圆括号的配对，
`[` `]` `{` `}` 原样进编码器。用 Anima 的真实分词器
（`comfy/text_encoders/anima.py` 的 `AnimaTokenizer`）逐条验证过。

两个数字定了这件事的优先级：Anima 自带索引 108,257 个标签里 **25,815 个含圆括号**，
其中 25,813 个会被解析器改写；另有 **104 个**更糟——`210 (reverse:1999)` 的 `:1999`
被当成权重，`1999` 这个词直接从提示词里消失。转义后全部 25,815 个精确还原
（`tests/Escape.cs` 跑全量，不抽样）。

判据必须是**词库认不认得**，不能是"长得像不像权重"：`210 (reverse:1999)` 里 `:1999`
是个合法数字，单看形状会被误判成权重而放过；反过来 `(chibi:2)` 词库不认、是用户手写的
权重，转义掉就把他的意图毁了。两个方向都踩得到，所以只能查库。

代价与边界：

- 手写进来、词库没有、又带括号的文本不转义（`hatsune miku (vocaloid)`——Danbooru 里
  她本名不带这个后缀）。那侧刻意保守：括号被剥掉但内容还在，通常无害；
  而**不会**毁掉权重语法。
- 逗号转义不了：Anima 索引里有 27 个标签自带逗号，而 ComfyUI 不认 `\,`；
  何况逗号是本工具自己的分隔符，不是 Anima 的。
- Qwen 的三个特殊 token（`<|endoftext|>` / `<|im_end|>` / `<|im_start|>`）会被分词器
  当成单个 token、解码成空串。词库里没有，手输会中招，转义救不了。

### 转义对解析层必须透明

正文里带上反斜杠之后，`TagSections.IsKnownTag` 会查不到那些标签，于是散文边界判定
（`PromptText.ProseStart` 第 1、3 条）和着色（`ColorSpans`）都会出错——
`210 \(reverse:1999\). An anime girl…` 整行会被判成散文、标签从中间列表里整个消失。

所以 `PromptText.Parse` / `SplitTags` / `ColorSpans` / `Summarize` 都带一个
`unescapeTags` 开关：**按原文定位、按字面量查库**。下标仍按原文算，着色区间和散文切片
因此不受影响。`tests/Escape.cs` 第 7 节同时钉住"传 flag 正确"和"不传就坏"——
后者是防止这个参数以后被当成可选优化删掉。

token 预算也按**编码器看到的**文本算：ComfyUI 会把 `\(` 的反斜杠吃掉再送分词器，
直接拿转义后的正文估算会多算那些反斜杠，括号标签一多就可能误报「超 512」。

### 复制时为什么还要再规范化一遍

转义发生在"写进提示词框"这一步（`CommitPrompt`），而**直接在框里打字/粘贴**不经过
标签列表、也就不会触发它。所以 `CopyPromptToClipboard` 复制前再跑一遍
`NormalizeEscapes` 兜底，并把结果写回框里。这一步**幂等**：已经转义过的标签带着
反斜杠、词库查不到，`ShouldEscape` 返回 false，不会再补一层。

## 撤销为什么是"快照式"而不是"反向操作"

`Core/PromptHistory.cs` 存的是**每一刻的完整文档状态**（标签序列 + 散文尾巴），
不是每一种操作的逆运算。理由是状态空间很小而操作种类很多：加、删、上移/下移、
拖动排序、改名、粘贴、规范化、重排、翻译、清空——其中粘贴和规范化会**批量**改动，
每一种都写一份逆运算的话，还得额外记住每个标签原来的下标；快照没有这些负担。

用法是**操作前记一笔**（`PushUndo`），所以撤销就是把上一个状态拿回来、重做就是把
当前状态推回去，两边共用同一个栈结构。几条定死的规矩：

- **只改内存，绝不落盘。** 撤销本身不写 `.txt`、不写提示词库。落盘仍旧走保存那条路，
  否则用户没按保存、文件却被改了——这是这个程序一直守的底线（见 `06-file-safety.md`）。
- **步数上限从最旧的一端裁**，`0` 表示关闭。越界值（负数、超大）在
  `MaxSteps` 的 setter 里收敛，所以手改 `settings.json` 填进一个荒唐的值也不会出事。
- **状态没变就不记**（`PromptSnapshot.SameAs`）。各命令都已经在自己的提前返回之后
  才 `PushUndo`，这里是兜底：记了一个"撤销了但界面没变"的点，用户只会以为功能坏了。

## 撤销历史为什么按文档身份分桶

`Core/PromptHistoryStore.cs` 按 `PromptDoc.Identity`（标注 = 图片全路径，
写标签 = `draft:<库条目 id>`）给每一份文档各存一条独立的历史。

**最初的做法是"换文档就清空"**（`ResetHistory`），理由写在 `PromptHistory.Clear` 的
注释里：撤销点里存的是上一份文档的标签，而撤销不写盘，跨文档撤销会让上一张图的
标签出现在当前文档里，用户接着一保存就写错了文件。这个理由本身成立，问题在于它
是个**靠纪律维持**的安全属性——换文档的路径有四处（`OpenLabelDocument`、`OpenDraft`、
`Select` 的空数据集分支、`LoadCurrent`），漏掉任何一处，症状都不是崩溃，而是静默写坏
一个 caption。分桶之后，一份快照**只能被它自己的文档取用**，这个属性变成结构上不可能
违反；顺带换回了本该有的能力：标完第 3 张翻到第 7 张、想起第 3 张改错了，回去时
撤销栈还在。

三条实现上的要点：

- **离开时记内容、打开时验一致。** 桶里存着"上次离开这份文档时它是什么内容"
  （`RememberCurrentDocument` 在换文档前调）。重新打开时对不上就说明这份文档被外部
  改过（别的编辑器、脚本、另一个实例），此时 `Attach` 会丢掉历史但保留桶，并记一条
  `history dropped (content changed outside)` 日志——不留日志的话，用户只会看到
  "撤销怎么没了"，无从判断是外部改了文件还是程序弄丢了。只需记"离开那一刻"：
  盘上内容正是那一刻写下去的，它就是唯一正确的基线。
- **新草稿的身份是共用键。** `DraftDoc.NewIdentity`（`draft:(new)`）被所有尚未入库的
  草稿共用，所以首次入库拿到 id 时必须 `Migrate` 到新键上。不搬的两个后果：那份草稿
  从库里重新打开时历史凭空消失；而下一份全新草稿**会继承**它的撤销栈。
  `OpenDraft(null)` 还要清掉共用键上的残留（被放弃、从未入库的那一份）。
- **上限是两层的。** 每份文档最多 `UndoMaxSteps` 步；仓库整体最多
  `DefaultMaxDocuments` 份，超出按 LRU 淘汰——但**优先淘汰"点开过却没编辑过"的桶**，
  这样浏览一遍数据集（或来回翻图）不会把早先真正编辑过的那几张挤出去。
  一步快照约 250 字节（`PromptSnapshot` 复制的是字符串**引用**，字符串不可变，
  所以跨快照共享是安全的），256 份 × 100 步约 6.4 MB 封顶。

换一个训练集目录会 `Clear()` 全部历史（`LoadFolder` 里按根目录比对）：桶是按绝对
路径分的，上一个数据集的那些实例不在当前工作集里。同一个数据集"重新载入"（F5）
**不**清——那正是要保住历史的场景。

历史只活在内存里，关掉程序就没了。跨重启保留需要额外一个历史文件，而且启动时要
逐条跟盘上内容重新校验——收益（关掉再打开还想撤销）远小于它引入的不确定性。

## `Ctrl+Z` 的加速键为什么这样挂

**不挂在菜单项上。** 菜单项的 `KeyboardAccelerator` 是**窗口级**的，挂上会劫持
提示词框里自己的撤销——这就是 `Ctrl+C/V` 当初只写
`KeyboardAcceleratorTextOverride` 作提示、真正绑定挂在列表上的同一个理由。
所以「编辑」菜单两项只有提示文字，实键由 `AddAccelIf` 挂到 `RootGrid`，并且带一个
"这次轮不轮到我"的判断。

实测有两点值得记下来（都在 `NOTES.md` 里有更细的排查过程）：

- **`RichEditBox` 会先吃掉 `Ctrl+Z` 并标记 Handled**，所以挂在 `RootGrid` 上的加速键
  在提示词框里**根本不会触发**（探针一行日志都没打）。也就是说"焦点在输入框里时
  归输入框"这件事是框架保证的，`AddAccelIf` 的判断只是第二道防线，不是机制本身。
- **`AutoSuggestBox` 外层的 `KeyDown`（冒泡）收不到 `Ctrl+Z`**——内部那个 `TextBox`
  已经把它处理掉了。所以「添加标签」框走的是 `PreviewKeyDown`（隧道，从根往下先经过
  这里）。判据是"框里空着时才归标签历史"：空框的原生撤销本来也无事可做，而
  "打完标签按回车、马上想反悔"正是最常按 `Ctrl+Z` 的时刻。

> 已知的既有瑕疵（**不是**这次引入的）：提示词框的原生撤销会被 `ApplyPromptColors`
> 的改色操作污染——`RichEditBox` 把字符格式改动也记进同一个撤销栈，于是每退一个
> 字符要按两三次 `Ctrl+Z`。`Windows.UI.Text.ITextDocument` 没有"暂停记录撤销"的
> API，所以没在这次的范围内处理。

## AI 助手：为什么提案走工具调用，而不是解析模型的话

`Core/AgentKit.cs` + `Core/TagAgent.cs`。模型给的改动**通过一个 `propose` 工具调用**
回来，而不是让它写一段 JSON、或者从它的自然语言里猜。

理由是**可核对**。`tool_call.arguments` 是服务端保证的合法 JSON，而小模型手写的
列表/JSON 格式极不稳定（实测会写成 `` - `1girl`, *solo* ``、或者把多个标签塞进
一个字符串——`ParseProposal` 因此要反复剥反引号和项目符号，剥一次会被空格挡住前导
反引号，这一点被 `tests/Agent.cs` 抓过）。更重要的是：**解析模型的话**意味着任何
格式意外都会变成"往训练集里塞一个谁也没看过的标签"，而这条路上已经有一条同类教训
（`TagSearchAgent` 的类注释：界面里可点的标签一律取自工具实际返回的行）。

### Known / Unknown 由代码算，不由模型说

判据是 `TagSections.IsKnownTag`，**和中间那个标签列表用的是同一条规则**。
词库不是全集（实测 679 个真实标签里 74 个查不到），所以查不到的**照旧列出来、
标成橙色**，只是提示。这里有一个具体反例值得记下来：`@syrstyle` 词库不认，却是
必须保留的画师触发词（不带 `@` 效果非常弱，见 `09-tags-vs-prose.md`）——所以
"认不得就改成散文"这种做法是错的，系统提示里明确要求 `@` 开头的原样留在标签里，
而 `AgentKit` 的回归测试里就钉着这条。

概念该走标签还是走散文，判据是**形状**而不是词库认不认得：单词/短语 → 标签（哪怕
词库没有）；成句的、或者表达空间/归属关系的 → 散文。

### 写入不在 agent 里

`TagAgent` 只产出提案，落到文档上由用户在界面上点「应用」（`ApplyAgentProposal`），
所以：

- 一次应用 = **一个撤销点**（直接动 `_pendingTags`，不走 `AddTagCore`——那个每次都会
  自己记一个撤销点，一条 18 个标签的提案会占掉 18 步）；
- "模型在没人看着的时候改了训练集"这件事**结构上不可能发生**。

散文的落法直接复用翻译器那条路（替换 → 换掉散文尾巴；追加 → `PromptText.AppendProse`
再回读），不另写一份：散文边界的规则在 `PromptText` 里，重复实现必然漂移。

### 图片：先缩、内联发、EXIF 要算

`Core/ImagePayload.cs`（碰 WinRT，所以**不在** `tests/corecheck.csproj` 里，
和 `ThumbnailLoader` 一样；尺寸那点数学单独放在可测的 `Core/ImageSizing.cs`）。

- **解码时就缩**：训练集单张 8.4 MB / 3258×3978，全尺寸解码一张约 52 MB 内存。
- **一律重编码成 JPEG**：原图可能是 8 MB 的 PNG，内联成 base64 还要再涨三分之一；
  长边 1024 的 JPEG 约 65–150 KB。
- **EXIF 方向要算进去**：方向 5–8 时解码器报的宽高是转置的，不管它长边就落在错的
  那一维上。实测 `优酱-智慧.png`（1080×612）→ 1024×580 / 65 KB。
- **内联而不是先上传**：训练集的图不该被传到第三方存储上；至少让"图出了这台机器"
  只发生在用户自己配置的那个接口上。

长边取 1024 的依据是实测的 token 代价（对 `deepseek-v4.1-flash` 量的）：图片 token
约等于像素数 / 1600，且每张图有一个约 200 token 的底。1024×1024 约 850 token，
而 3258×3978 直接发是 8000 token 量级，还会被很多接口按体积拒收。

### 收尾那一次为什么复用同一个 messages 列表

轮数用完时（`MaxRounds = 4`）要"不带工具再问一次"，此时**沿用同一个 messages 列表、
只把工具列表清空**，而不是另起一条纯文本请求：换请求就等于把第一轮挂上去的那张图
丢了，而"读图"正是最容易把轮数用完的场景。`ChatWithToolsAsync` 在工具列表为空时
**不下发 `tools` 字段**（不是发 `"tools": []`——有些服务会当成"要求调工具但没有工具
可用"而报错）。

### 对话为什么换文档就清空

撤销历史能按文档身份分桶（它有"离开时的内容"可以对账），对话不能：历史里带着上一份
文档的画面，而没有任何东西能校验"这段对话还配得上当前这份文档"。所以
`AttachHistory()` 里顺带清空（那是换文档的唯一漏斗），而不是在四处调用点各清一次。

### 翻译器为什么没被替换掉

助手面板只顶替右栏的**位置**，翻译器那条确定性的路仍然是默认（`AgentEnabled`
默认关）。它是四轮实测调出来的：长度跟输入走（"至少两句"会稳定编造）、方向词不许丢、
不许加质量词——全部记在 `LlmClient.ProseSystemPrompt` 的长注释里。让"读图 + 提案"
去承担那段已经收敛的翻译职责，等于把一条验证过的路重新打开，而这次是写进训练集。

### 多工具：`ChatWithToolsAsync` 的那次泛化

原来是单工具、参数 schema 硬编码成 `query: string`。现在收 `IReadOnlyList<AgentTool>`，
空列表=不给工具。工具说明也顺手合并了：`search_tags` 与 `web_search` 的说明分别由
`TagSearchAgent.ToolDescription` 和 `AgentKit.WebSearchTool` 单点定义，
`TagTranslator` / `TagSearchAgent` / AI 助手三处引用同一份——同一个工具在两个入口
表现不同是最难查的 bug。

## 模型能力为什么是"问服务端"而不是"让用户填"

标准 OpenAI 的 `GET /models` 只保证 `id`，但**兼容实现普遍加了能力字段**，实测
DeepSeek 报的是（`tests/Models.cs` 里存着逐字节的原样响应）：

```json
{"id":"deepseek-flash","name":"DeepSeek-V4.1-Flash","context_window":1048576,
 "max_output_tokens":393216,"input_modalities":["text","image"],
 "effort":{"supported_levels":["low","high","max"],"default_level":"high"}}
```

所以"这个模型吃不吃图"有确定答案，不需要用户手工声明，也不需要发一次试探请求。
`ModelInfo` 把这些字段都解出来，设置里那行提示直接报（含"仅文本输入"这样的
结论），AI 助手据此决定「带当前图片」能不能勾。

**`SupportsImage` 是三态，这一条是设计要点。** 它返回 `bool?`：

| 服务端说 | 值 | 行为 |
|---|---|---|
| `input_modalities` 含 `image` | `true` | 放行 |
| 报了但只含 `text` | `false` | 拦下，并说明原因 |
| **根本没报这个字段** | `null` | **放行** |

第三行是 llama-server 那一类：它只报 `meta{n_ctx,ftype,size}`。把"不知道"当"不支持"
会把本来能用的配置判死，而且用户完全无从察觉——`tests/Models.cs` 第 8、10 节专门
钉着这条。拦截逻辑抽成纯函数 `LlmClient.CanAttachImage(bool?, bool)` 而不是留在
`MainWindow` 里，就是为了让这条规则能在 net10 回归里被测到。

缓存只在 `LlmClient` 内部（`_caps`，按「接口地址 + 模型名」索引），**不落盘**：
条目极少、只在会话内有用，丢了只多花一次几百毫秒的 GET——不值得再引入一个要与
配置文件同步的文件。键必须带接口地址，同一个模型名在本地网关和云端是两回事。
`EnsureCapsAsync` 对每个键**一辈子只试一次**（含失败），否则一个不实现 `/models`
的网关会让每次翻译都多等一次超时。

## 推理档位：两种服务端、两种机制，以及 `supported_levels` 不是门槛

原来设置里只有个 bool「关闭思考链」，代码只发
`chat_template_kwargs.enable_thinking=false`，注释里的担心是"下发给云端会 400"。
**实测推翻了这个担心，真正的问题更隐蔽**：DeepSeek `api.deepseek.com` 照收这个
字段、回 200，然后**静默忽略**——同一端点、同一条提问、同一个 `max_tokens`：

| 请求体 | 服务端返回的 `reasoning_content` |
|---|---|
| 只有 `chat_template_kwargs` | **69 字符**（思考照常发生） |
| 加上 `reasoning_effort: "none"` | 0（真的关掉了） |

所以那个 bool 在云服务上一直是**空转**的：用户以为省了 token，实际每次都在为思考
付费；`ReasoningHeadroom` 那句"关思考时预算就是用户设的那个值"也不成立。

**为什么从 bool 升级成档位选择器。** 那个 bool 只能表达"关"与"不指定"两态，而
服务端提供的是连续强度——用户没法要求"少想一点但别完全不想"。升级后配置里是
`ReasoningEffort`：空串 = 自动（不下发，跟随服务端 `default_level`），其余取八个
档位之一。旧的 bool 迁移规则是 `true → "none"`、`false → ""`（见
`AppSettings.MigrateThinking`）；迁移过就把旧键置空，靠
`JsonIgnore(WhenWritingDefault)` 让它在下次保存时消失，不留一个和档位说法不一致的
死字段。

**`effort.supported_levels` 是描述性的，不是硬约束**——这一点推翻了本仓库早先
写下的"按它发，别硬编码一份全局清单"。给 `deepseek-flash` 连发它**没声明**的档位：

| 发出的档位 | 在 `/models` 的 `supported_levels`(low/high/max) 里？ | 结果 |
|---|---|---|
| `minimal` / `medium` / `ultra` | 否 | **HTTP 200** |
| `none` | 否 | **HTTP 200**，且 `reasoning_content` = 0 |
| `max` | 是 | HTTP 200 |
| `bogus` | —— | **422**，正文列出全部合法值 |

也就是说硬约束是一份**全局词表**（422 原话：
``expected one of `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `ultra`, `max` ``），
`supported_levels` 只说明"这个模型有意义的档位"。所以
`LlmClient.EffortVocabulary` 就是那八个，界面另外把模型声明的子集写进提示行。
顺带一条：`reasoning_effort` 是**接口级**的，只吃文本的 `deepseek-v4-pro` 收
`none` 同样回 200 且思考为 0——所以判据是"服务端声明过 `effort`"，不是"当前模型
的 `supported_levels` 里有它"。

于是规则是 `LlmClient.EffortToSend(档位, 服务端声明过 effort 吗)`：自动→不发；
服务端没声明→不发（llama-server 压根没这个参数，没有证据证明它会忽略一个不认识
的字段，不冒 400 的风险）；不在词表内→不发（只可能来自手改 settings.json，宁可
退回"自动"也不打红请求）。**代价是"支持但不报"的网关会静默不下发**，所以设置页
那个提示行必须把这件事写出来——它不是装饰，"选了一个不生效的档位"本身看不出来。

**带工具那条路仍然不跟档位走**：llama-server + Qwen3 实测关掉思考后模型不再发出
`tool_calls`，搜索工具等于失效（见 `ChatWithToolsAsync` 的注释）。两件事的正确取值
相反，所以按调用需要决定，不跟着档位走。

## 分栏比例为什么按模式各存一套

两个模式的分栏语义不同（图片 / 标签 / 提示词 vs 提示词库 / 标签 / 提示词），
共用一组值会让一个模式里拖过的布局把另一个模式改掉。
